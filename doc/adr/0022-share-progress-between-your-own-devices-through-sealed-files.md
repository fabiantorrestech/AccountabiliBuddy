# 22. Share progress between your own devices through sealed files

Date: 2026-10-21

## Status

Accepted

## Context

The user is putting AccountabiliBuddy on a work desktop. It is always on the office network, has no camera, and has Google Drive for desktop signed in to the user's personal account. They want one running log of focused time across all their devices (the work desktop, the home laptop, the Pixel 7 and the Pixel Watch), the day plan going both ways, and their settings kept in step. The ADR 14 link can't reach that desktop. The PC listens only on networks Windows marks Private, and office networks are usually Domain networks. A program accepting connections on a company network is what IT flags, and the phone's Wi-Fi at the office is usually kept apart from the desks' Ethernet. So progress has to travel by routes that need no incoming connection, and on the work desktop the app itself should open none.

The project's hard rule keeps everything local except a short list of named connections (ADR 9, 12, 14, 15, 21). ADR 15 lets the readable part of activity history reach the user's paired devices, but only over the ADR 14 link. The unstarted device sync plan (doc/plans/device-sync.md) proposed that data may leave a device only to the user's own devices and a self-hosted server, end-to-end encrypted, and never to third-party services. A folder in Google Drive is a third-party service, so it needs a decision of its own. .NET and Android both ship AES-GCM, HKDF and Deflate, so sealing files needs no new library. The user approved the designs this follows (doc/plans/2026-10-21-device-sync-design.md and doc/plans/2026-10-21-devices-and-computer-types-design.md) on 2026-10-21.

## Decision

We will let progress, the day plan and shared settings leave a device only as sealed sync files, and only to the user's own devices. Each device writes one file of its own: its device card (id, name, kind, app version, when it wrote, its methods), the last 14 days of its counted focus sessions and drift with only the readable fields ADR 15 allows (times, app, site and its section, profile names), its day plan with its version and edit time, and its profiles, sleep and day bar settings. A device with Activity history off sends no sessions or drift. Window titles, full addresses, OCR text, early-end reasons and notes on added sessions are never in a file. Each device's Cold Turkey expected blocks never sync, because blocklists can differ between devices.

Every file is sealed with AES-256-GCM under a key derived with HKDF-SHA256 from a 40-character link code holding 200 random bits. The first device makes the code. The others get it by scanning a QR code, over the ADR 14 link, or by the user typing it on a computer without a camera. The code is stored only under DPAPI on the PC and the Android Keystore on the phone, and it never passes through anything that carries the files. The sealed bytes may be carried by QR codes the PC shows, by sync files the user shares or imports, by a cloud folder the user picks (on a PC, a folder of Google Drive for desktop, which the app sees as a plain folder), or by the ADR 14 link, which now also carries the other devices' files so the phone can bring them home. File names in a folder are opaque ids, never device names, so Google, the employer or anyone else with access to the folder or a file can read neither who wrote it nor what it says. On a work computer AccountabiliBuddy opens no connection for this: it only reads and writes files in the folder, and Drive for desktop does the uploading. Every method is a switch per device, and nothing is written or sent by a method until its switch is on. A receiving device applies what arrives by its own rules: a stricter profile change at once, a looser one only after its own looser-change delay and never during a session, and a day plan that clashes with a local edit asks the user.

This amends the project CLAUDE.md's "Local only" hard rule, and for this purpose replaces doc/plans/device-sync.md's "never third-party services": a cloud folder the user chooses may hold sealed files. How the phone reaches that folder (Google sign-in in the app, or a separate app that keeps the folder on the phone) is settled by a test on the user's Pixel 7 and, if it needs Google sign-in, recorded in its own ADR.

## Consequences

Focus progress from the work desktop reaches the laptop, the phone and the watch without the desktop accepting or opening a connection of its own, and the user chooses per device which routes to use. The rule widens from "only the named connections" to "and sealed files to your own devices, through carriers you choose". Google learns that encrypted files of some size appear in the folder and when, but not what's in them or which device wrote them. The link code becomes the one secret that protects all of it: anyone who has it can read every device's files, so it is shown only on the user's own devices, leaving the group forgets it on that device, and replacing it means every device joins again. A lost device that holds the code and received files exposes up to 90 days of the other devices' readable history, as under ADR 15. The sealed format ("ABS1", a 4-byte group id, a 12-byte nonce, then AES-GCM over Deflated camelCase JSON with its tag) must stay byte-compatible between C# and Kotlin, which cross-language checks keep honest, and changing it needs a format version that older apps refuse. A snapshot file per device rather than an event log means a receiver simply replaces its copy of that device's part, so edits and deletions need no merging of histories, but every file carries 14 days and a busy day can need several QR codes. Live control, such as starting or ending a session on another device, still goes only over the ADR 14 link.
