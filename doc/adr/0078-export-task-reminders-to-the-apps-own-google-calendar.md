# 78. Export task reminders to the app's own Google calendar

Date: 2026-11-11

## Status

Accepted

Amends [9. Allow read-only calendar connections](0009-allow-read-only-calendar-connections.md) (reading stays as it was; this adds one write path)

## Context

The Tasks redesign (ADR 76, `05 Shared behaviour` §7, `02 Data model and sync` §6) gives tasks a due date and up to five reminders, and asks for them to appear in the user's Google Calendar, one event per task with the reminders as the event's reminder overrides. Until now the app only read calendars: ADR 9 allows read-only iCal downloads and Google Calendar with the `calendar.readonly` scope, and the hard rules say any other connection needs a new ADR. Writing events needs a broader Google permission, and the user must consent to it again in their own Google Cloud OAuth app (the app uses the user's own client, set up through `GoogleSetupSteps`).

Google offers `https://www.googleapis.com/auth/calendar.app.created`, which lets an app create secondary calendars and see, create, change and delete events only on the calendars it created. It cannot read or change the user's other calendars. Writing into the user's main calendar instead needs `https://www.googleapis.com/auth/calendar.events`, which lets the app change events in every calendar the user has.

The owner decided (2026-11-11): export task reminders and due dates; by default into the app's own calendar, with experimental support for adding them to another (main) calendar as well.

## Decision

The app may write to Google Calendar for task reminders and due dates only, through the existing calendar code in `CalendarNetwork` / `CalendarSyncService`, with the user's own OAuth client.

By default it asks for `calendar.app.created` in addition to `calendar.readonly`, creates one secondary calendar named "AB Reminders", and writes every exported event there: a task with a due date becomes an event at its due time, and a task with reminders but no due date becomes an anchor event, with the task's reminders as the event's reminder overrides (Google allows five, which is why a task holds at most five). It is one event per task, updated when the task's title, reminders or due date change and deleted when the task is finished, archived or deleted.

As built (M3 task 3, `TaskCalendarMapping`, `TaskCalendarDiff`, `GoogleCalendarWriter`, `TaskCalendarExportService`):

- A due date with a time is a 15-minute event at that time. A due date alone follows "Tasks with a date but no time" (device-local in `tasks.reminderSettings`; owner, 2026-11-11): "Timed at 9:00 AM" (the default) makes a 15-minute event at 9:00 AM, the time such a task's reminders count from, so same-day reminders like "At start time" go on it; "All-day event" makes an all-day event, and since Google counts an all-day event's reminders back from its midnight start, reminders on the day itself are left off (they still ring in the app; the log counts them). Changing the setting updates the affected events in place (same ids). Reminders but no due date (only "at" reminders can ring then): the anchor is a 15-minute event at the task's last reminder, every reminder an override before it, so each still rings at its own time. Overrides are 0 to 40320 minutes (four weeks), at most five; events are marked free.
- Event ids are fixed per task (`ab` + the task id's hex digits, Google's base32hex alphabet), so every device and a reinstall reach the same event and never make a second one (an id Google already holds, also a deleted one, is replaced). The events this PC wrote are recorded device-local (document `tasks.calendarExport`: account, the "AB Reminders" id, per task the calendar, event id and a hash of the content; no text), and only recorded events are ever changed or deleted. The synced `calendarEventId` on reminders is left unset: writing it from the exporter would stamp the task's reminders field and could override a reminder edit from another device that hasn't arrived yet. Because the ids are shared, a PC deletes an event only when the task is finished, archived, deleted, switched off or has no due date or reminder left; a task that still wants its event but is no longer kept on this PC (its devices no longer include it, or the PC isn't in a group yet) is only forgotten here, its event left for the devices that keep it.
- "AB Reminders" is identified by its recorded id. A calendar the account owns with that name (one from an earlier install) is reused only after Google accepts a change to the calendar itself (its description), which Google allows only to full calendar access, never asked for, or to `calendar.app.created` for a calendar this OAuth client made; so a calendar the user made, or one an earlier Cloud project made, is never written to, even with `calendar.events` granted. If Google later refuses or loses "AB Reminders", the app forgets it and makes a new one, at once the first time and then at most once per backoff wait.
- Existing users: export stays off (`NeedsConsent`) until they press Allow (Settings, M7), which runs Google sign-in again for `calendar.readonly` + `calendar.app.created` with `include_granted_scopes`; the account must be the connected one, and its new refresh token replaces the old. New connections still ask read-only only. Granted scopes are read from Google's token answers, so a sign-in without the scope turns export off again by itself. Reading calendars never needs the new scopes.
- The reading side leaves "AB Reminders" out by its recorded id (its events are the user's tasks, already in the app); a user calendar that only shares the name is still read.
- Writes follow every change of the tasks or the settings two seconds later, in the background; a failure waits 30 seconds, doubling to 30 minutes, and never stops the app; a 403 Google marks as a rate limit waits the same way. With nothing to write the app makes no call to Google at all.
- Fix round 2: a task kept on other devices is only forgotten while it still has an event to want (a due date or a reminder); otherwise this PC deletes it, so no event is orphaned when the keeping device never wrote it. A claim refused as "insufficient scope" also means "not ours" (a new calendar is made). A PC with no record of "AB Reminders" hides it from reading by its name plus the description only the app writes (a read-only check). With the account's pick made on another device and no consent here, this PC deletes its own "AB Reminders" copy of a task's event only after a read shows the same event id in the picked calendar; a pick only taken over at the upgrade (adopted stamp) counts as this PC's own, not as "picked elsewhere"; with "Sync task lists" off another device's pick is ignored here.

An experimental option, off by default and labelled as experimental, lets the user pick one of their own calendars for due-dated tasks: those tasks' events then go there instead of to "AB Reminders" (still one event per task; tasks without a due date stay in "AB Reminders"). Only when the user turns it on does the app ask for `calendar.events` (incremental consent); turning it off stops writing there, deletes the events the app made there and puts them back in "AB Reminders". Without that consent nothing is written outside the app's own calendar: if it is taken back, the app stops writing there, keeps its records of the events it made there (so they can be cleaned up once consent is back) and asks for consent again.

Amended (2026-11-11, owner): the picked calendar is the account's setting, the same on all the user's devices (ADR 76's `taskAccountSettings` part), because two PCs with different picks made two events for one task and rang twice. The consent stays per device. A PC without `calendar.events` whose account pick was made on another device (which had the consent) exports its due-dated tasks nowhere, not to "AB Reminders" either, and deletes the "AB Reminders" events it recorded for them, so no task gets a second event; the devices with the consent write them, with the shared event ids. A pick made on the PC itself keeps its tasks' events where they are until consent is given, as before. Changing the account's pick moves each device's own events (deleting only the ones it made).

Only a task's title and times leave the device. Notes, steps, tags, labels, reasons and window data never do. The setting "Add new reminders to" (Google Calendar, the default; Nowhere; device-local in `tasks.reminderSettings`; the picked calendar is the account's, see the amendment above) and the per-task "Add to Google Calendar" switch decide what is exported: a task takes the setting's value when it gets its first reminder or due date (`TaskCalendarOptIn`), and existing tasks are never exported without the user turning it on for them. Windows Calendar is not built (no API usable from the desktop app without new connections was confirmed).

## Consequences

The app gains its first write path to an outside service other than the user's own Drive folder and relay: a mistake can now create or delete events in the user's calendar, so writes are limited to events the app created and recorded (fixed per-task event ids, recorded device-local in `tasks.calendarExport`), and the main-calendar option stays experimental until it has been used for a while. Existing users must re-consent before export works; until then export is off and the app keeps reading calendars as before. A due date without a time becomes a timed event at 9:00 AM by default so its same-day reminders reach Google; users who prefer an all-day event lose those reminders on the Google side (they still ring in the app). The picked calendar is the account's (amended above), so devices no longer disagree about it; a device without the consent leaves those tasks to the ones that have it, so with no consenting device left those tasks have no event until consent is given again. The setup guide's scope list and the "What syncs / what leaves this PC" texts must name the new scopes. Task titles now appear in the user's Google account, which the user opts into by choosing Google Calendar in "Add new reminders to".
